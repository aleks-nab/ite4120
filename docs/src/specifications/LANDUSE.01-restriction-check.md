# LANDUSE.01 · Land use restriction check

> **LANDUSE.01** · state **Proposed** · traces from [LANDUSE-US-001](../user-stories/LANDUSE-US-001.md)

## Description

A landowner enters a cadastral number and sees the land use restrictions on the
plot, each explained by a rule from this component's **rule catalogue**: what is
forbidden, what is allowed only with consent, whose consent is needed, and the
legal basis. The owner can save the result as a **pre-check** and ask the
municipality a question before a formal building permit application.

The restrictions themselves are owned by the national restrictions register
(KPOIS, `kyKitsendusedAvalik`) and are looked up through a registry adapter —
the imitated register in this course, X-Road-shaped in production. They are
**not** kept as a copy, except as a snapshot inside a saved pre-check, which
records what the owner was shown on that day.

Excluded: a map, ID-card / Mobile-ID / Smart-ID login (mock auth only), the
building permit application itself, requesting consent, a complete rule
catalogue (the first version covers the most common restriction types only).

## Data model  *(→ session 2)*

Schema `landuse` (changesets `landuse-schema`, 01–04, 90 demo). One reference
table, three business tables, five foreign keys.

| Table | Field | Type | Rules |
| --- | --- | --- | --- |
| `landuse.restriction_type` | `code` PK | text | reference list, natural key, e.g. POWER_LINE_ZONE, GAS_PIPELINE_ZONE, ROAD_PROTECTION_ZONE, SHORE_BUILDING_EXCLUSION, HERITAGE_PROTECTION, NATURE_PROTECTION |
| | `name` | text | required; display name in Estonian |
| `landuse.restriction_rule` | `id` PK | bigint | from `core.seq_id` |
| | `restriction_type_code` | text | required; FK → restriction_type |
| | `forbidden` | text | required, ≤2000; what may not be done in the zone, in plain language |
| | `allowed_with_consent` | text | optional, ≤2000; what may be done only with consent |
| | `consent_party` | text | optional, ≤255; whose consent is needed (e.g. "owner of the power line") |
| | `legal_basis` | text | required, ≤500; act and section |
| | `valid_from` | date | required |
| | `valid_until` | date | optional; **not before `valid_from`** |
| | `sys_*` | — | platform columns, trigger-managed |
| `landuse.pre_check` | `id` PK | bigint | from `core.seq_id` |
| | `reference_number` | text | required; generated by the application; **unique among active rows** |
| | `client_request_id` | text | required; generated by the form once per check; **unique among active rows** — saving twice creates one pre-check |
| | `cadastral_code` | text | required; **format `NNNNN:NNN:NNNN`** — an identifier, a string, never a number |
| | `plot_area_m2` | numeric(12,2) | optional; plot area returned by the register; **> 0** |
| | `planned_building` | text | required, ≤1000; the owner's description |
| | `contact_email` | text | required, ≤255; e-mail format |
| | `status` | text | required; one of NEW, ANSWERED; starts as NEW |
| | `officer_comment` | text | required when status is ANSWERED, ≤2000 |
| | `register_complete` | boolean | required; false when the register reported hidden restrictions or did not answer |
| | `sys_*` | — | platform columns, trigger-managed |
| `landuse.pre_check_restriction` | `id` PK | bigint | from `core.seq_id` |
| | `pre_check_id` | bigint | required; FK → pre_check |
| | `restriction_type_code` | text | required; FK → restriction_type |
| | `restriction_name` | text | required, ≤255; as returned by the register |
| | `restricting_object_owner` | text | optional, ≤255; as returned by the register |
| | `legal_basis` | text | optional, ≤500; as returned by the register |
| | `affected_area_m2` | numeric(12,2) | optional; **≥ 0** |
| | `rule_id` | bigint | optional; FK → restriction_rule — the rule shown at the time of the check; empty when no rule existed |
| | `sys_*` | — | platform columns, trigger-managed |

Relationships (cardinality):

- one `restriction_type` — many `restriction_rule` (a type can have successive rules over time);
- one `pre_check` — many `pre_check_restriction` (one row per restriction found on the plot);
- one `restriction_type` — many `pre_check_restriction`;
- one `restriction_rule` — many `pre_check_restriction` (the same rule shown on many checks).

Platform rules followed: business tables get `id` from `core.seq_id`, the
`sys_*` columns and `core.create_table_metadata()`; soft delete via
`sys_status`; uniqueness among active rows only; identifiers (cadastral code,
reference number) stored as text; demo rows (a few rules and one pre-check)
under `context:demo`.

## API  *(→ session 3)*

Base path `/api/landuse`. A cadastral code in a path is sent as is
(`78401:101:0123`); a malformed one is a 400 before any register call.

| Method + path | Does | Failure answers |
| --- | --- | --- |
| `GET /api/landuse/plots/{cadastralCode}/restrictions` | the check: restrictions from the register adapter, each joined with the rule valid **today** for its type; plot area; `registerComplete` flag | 400 malformed code · 404 unknown plot · 502 register down |
| `GET /api/landuse/restriction-types` | the reference list | — |
| `GET /api/landuse/rules` | paged rule list: `typeCode`, `validOn`, `limit`, `offset`, `sort` | — |
| `GET /api/landuse/rules/{id}` | one active rule | 404 |
| `POST /api/landuse/rules` | add a rule; answers **201 + Location** | 400 validation (unknown type, `validUntil` before `validFrom`) |
| `PUT /api/landuse/rules/{id}` | update a rule | 400 · 404 |
| `DELETE /api/landuse/rules/{id}` | retire (soft) — **204** | 404 |
| `POST /api/landuse/pre-checks` | save a check as a pre-check, with the restrictions and rule ids shown; answers **201 + Location**; the same `clientRequestId` again answers **200** with the existing pre-check | 400 validation |
| `GET /api/landuse/pre-checks` | paged list: `status`, `limit`, `offset`, `sort` | — |
| `GET /api/landuse/pre-checks/{id}` | one pre-check with its restrictions and the rules shown | 404 |
| `PUT /api/landuse/pre-checks/{id}/answer` | officer's answer: status ANSWERED + comment | 400 empty comment · 404 · 409 already answered |
| `GET /api/landuse/reports/restriction-summary` | count of pre-checks per restriction type and per consent party, `from`–`to` | 400 `to` before `from` |
| `GET /mock-registry/kpois/restrictions/{cadastralCode}` | **the imitated restrictions register** (local profile only), answering in the shape of KPOIS `kyKitsendusedAvalik`: per restriction `nahtuseLiik`, `nimi`, `seaduslikAlus`, `kpoOmanik`, `pindala`; a few fixed demo plots | 404 unknown plot |

Every error is `application/problem+json`. All `/api/**` endpoints require
`Authorization: Bearer <user>` (mock auth); the API contract is live at
`/swagger-ui.html`.

**Registry adapter.** Two layers, as in the worked example: wire records keep
the register's Estonian field names verbatim (`nahtuseLiik`, `pindala` …); one
mapper turns them into the component's own model. Register types are mapped to
`restriction_type.code`; an unknown register type is shown with its own name
and legal basis and no rule.

**As implemented** *(settled in session 3)*:

- **Check answer:** `{cadastralCode, plotAreaM2, registerComplete, restrictions[]}`; each
  restriction is `{restrictionTypeCode, restrictionName, restrictingObjectOwner, legalBasis,
  affectedAreaM2, rule}`, named after the `pre_check_restriction` columns. `rule` is the full
  rule valid today, or `null`. When rule periods for a type overlap, the rule that started
  latest wins.
- **Wire shape of the imitated register:** a plot is `{katastritunnus, pindala,
  varjatudKitsendusi, kitsendused[]}`. `pindala` is the plot area. `varjatudKitsendusi = true`
  means the register hides some restrictions, so we answer `registerComplete = false`.
  Each entry of `kitsendused` carries the five fields above.
- **Type mapping (`nahtuseLiik` → `restriction_type.code`):** ELEKTRIPAIGALDISE_KAITSEVOOND →
  POWER_LINE_ZONE, GAASIPAIGALDISE_KAITSEVOOND → GAS_PIPELINE_ZONE, TEE_KAITSEVOOND →
  ROAD_PROTECTION_ZONE, RANNA_EHITUSKEELUVOOND → SHORE_BUILDING_EXCLUSION,
  MALESTISE_KAITSEVOOND → HERITAGE_PROTECTION, LOODUSKAITSELINE_PIIRANG → NATURE_PROTECTION.
  Any other type is shown with `restrictionTypeCode: null` and `rule: null`.
- **Demo plots:** `78401:101:0123` matches the demo pre-check (power line and local road).
  `78401:102:0045` has a shore zone, a type we have no rule for and hidden restrictions.
  `79501:001:0001` has no restrictions. `99999:999:9999` makes the register answer 503,
  so the check gives 502. Any other well-formed code is 404.
- **Rule list sort keys:** `restrictionTypeCode`, `validFrom`, `validUntil` (prefix `-` for
  descending). An unknown key is a 400.
- **Open for the pre-check step:** `pre_check_restriction.restriction_type_code` is required,
  but a register type with no counterpart has no code. Saving such a restriction needs either
  a nullable column (a new changeset) or a catch-all type such as `OTHER`.

**Failure policy:** **fail closed** for the check — without the register there
is nothing to explain, so the owner gets 502 "register unavailable, try again"
and no partial answer. Everything else (rules, saved pre-checks, the report)
stays fully usable when the register is down. Rationale: a partial list of
restrictions looks complete and could mislead an owner into building.

## Business tests

1. **A cadastral number must have the Estonian format.**
   Given the input `78401-101-0123`, when the owner checks it, then the check
   is refused with "cadastral number must have the format NNNNN:NNN:NNNN".
2. **A rule cannot end before it starts.**
   Given a rule with `valid_from` 2026-10-01, when it is saved with
   `valid_until` 2026-09-01, then it is refused with "valid until must not be
   before valid from".
3. **An answered pre-check carries the officer's comment.**
   Given a pre-check with status NEW, when the officer sets it to ANSWERED
   without a comment, then the change is refused.
4. **Saving twice creates one pre-check.**
   Given an owner who presses "Save" twice for the same check (the same
   `clientRequestId`), when both requests arrive, then exactly one pre-check
   exists and the second request answers 200 with it.
5. **A saved pre-check remembers the rule it showed.**
   Given a pre-check that showed rule R for a power line zone, when R is later
   retired and replaced by rule R2, then the pre-check still shows R.
6. **The register being down never produces a partial answer.**
   Given the restrictions register does not answer, when the owner checks
   `78401:101:0123`, then the answer is 502 with "register unavailable, try
   again" and no restrictions are listed.
